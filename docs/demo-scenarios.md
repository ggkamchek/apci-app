# Сценарии демонстрации (защита диплома)

---

## Подготовка

Запущены: Chat API, Центр Безопасности, Desktop, Admin UI.  
Два физических устройства (или VM) — Device 1, Device 2.

---

## E2E (модуль Пети)

### Сценарий 1: Установка E2E-сессии

1. User A регистрируется на Device 1.
2. User B регистрируется на Device 2.
3. A добавляет B в контакты; B добавляет A.
4. A отправляет сообщение B.
5. **Ожидание:** B видит расшифрованный текст; на сервере — только ciphertext.

### Сценарий 2: Статусы сообщений

1. A отправляет сообщение B.
2. **Ожидание:** у A — «отправлено» → «доставлено» → «прочитано» по мере подтверждений.

### Сценарий 3: Присутствие и typing

1. B онлайн — у A отображается «в сети».
2. B набирает текст — у A «печатает…».
3. B закрывает приложение — «не в сети».

### Сценарий 4: Локальный поиск

1. A ищет слово в истории чата с B.
2. **Ожидание:** результаты на клиенте; сервер не получает поисковый запрос.

### Сценарий 5: Метаданные без содержимого

1. Показать в БД чатов: есть `from`, `to`, `timestamp`, ciphertext.
2. **Ожидание:** plaintext отсутствует.

## Центр Безопасности (модуль Sudeeneess)

### Сценарий 6: Связь по устройству

1. User A регистрируется на Device 1.
2. User B регистрируется на Device 1 (второй аккаунт — разрешён в MVP).
3. Открыть админку.
4. **Ожидание:** ребро A—B, тип `same_device`, высокий вес.

### Сценарий 7: Общие контакты

1. User A (Device 1) и User B (Device 2) оба добавляют User D в контакты.
2. **Ожидание:** ребро A—B, тип `shared_contact`.

### Сценарий 8: Переписка с одним человеком

1. User A (Device 1) и User B (Device 2) оба переписываются с User D.
2. **Ожидание:** рёбра `communicates_with`; в админке видна связь A—B через общего собеседника или прямое ребро.

### Сценарий 9: Автономность Центра

1. Остановить Центр Безопасности.
2. User A отправляет сообщение User D.
3. **Ожидание:** чат работает.
4. Запустить Центр.
5. Новые события снова появляются в админке.

---

## Совместный сценарий

### Сценарий 10: Полный поток

1. User A и User B на разных устройствах — E2E-переписка.
2. User C создаёт второй аккаунт на устройстве User A.
3. В админке: C связан с A (`same_device`).
4. C и A оба общаются с D — усиление связей в графе.
5. **Вывод:** платформа обеспечивает приватную переписку и параллельно накапливает данные для анализа мультиаккаунтинга.

## Что показать комиссии устно

| Вопрос | Ответ |
|--------|-------|
| Где ключи? | Только на клиенте |
| Видит ли сервер сообщения? | Только ciphertext |
| Как ловите мультиаккаунтинг в MVP? | Граф связей: устройство, контакты, переписка |
| Почему не баните сразу? | Сначала наблюдение, потом правила — осознанная фаза |
| Почему Центр отдельно? | Автономность, изоляция данных безопасности |
