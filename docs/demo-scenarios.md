# Сценарии проверки и демонстрации

Пошаговые сценарии для QA, демо заинтересованным сторонам и регрессионной проверки после изменений.

---

## Подготовка

```powershell
cd D:\Goalang\apci-app
.\scripts\dev.ps1 -Restart
```

Запущены: Chat API, Центр Безопасности, Admin UI.  
Для E2E-сценариев — два устройства (или VM): Device 1, Device 2.  
Для antifraud на одном ПК достаточно одного устройства.

| Сервис | URL |
|--------|-----|
| Admin UI | http://localhost:8081/admin/ |
| Токен | `dev-admin-token` |

## E2E-шифрование

### Сценарий 1: Ручная отправка ciphertext по UUID (работает сейчас)

1. User A регистрируется на Device 1.
2. User B регистрируется на Device 2.
3. Оба пользователя выполняют инициализацию E2E bundle.
4. A вставляет UUID пользователя B в E2E-форму и отправляет сообщение.
5. B открывает inbox.
6. **Ожидание:** B видит расшифрованный текст; на сервере — только ciphertext.

### Сценарий 2: Статусы сообщений (запланировано)

1. A отправляет сообщение B.
2. **Ожидание:** у A — «отправлено» → «доставлено» → «прочитано» по мере подтверждений.

### Сценарий 3: Присутствие и typing (запланировано)

1. B онлайн — у A отображается «в сети».
2. B набирает текст — у A «печатает…».
3. B закрывает приложение — «не в сети».

### Сценарий 4: Локальный поиск (запланировано)

1. A ищет слово в истории чата с B.
2. **Ожидание:** результаты на клиенте; сервер не получает поисковый запрос.

### Сценарий 5: Метаданные без содержимого (работает сейчас)

1. Показать в БД чатов: есть `from`, `to`, `timestamp`, ciphertext.
2. **Ожидание:** plaintext отсутствует.

## Центр Безопасности

### Сценарий 6: Связь по устройству (клоны)

1. User A регистрируется на Device 1.
2. User B регистрируется на Device 1 (второй аккаунт с того же ПК).
3. Открыть админку → **Связи** или **Обзор**.
4. **Ожидание:** ребро A—B, тип `same_device`, высокий вес.

### Сценарий 7: Расследование по UUID

1. Скопировать UUID аккаунта A из админки или API.
2. Вкладка **Расследование** → вставить UUID.
3. **Ожидание:** карточка аккаунта, связанные устройства и аккаунты.

### Сценарий 8: Расследование по хешу устройства

1. Вкладка **Устройства** → скопировать `device_hash`.
2. **Расследование** → вставить хеш (32 символа, без дефисов).
3. **Ожидание:** список аккаунтов с этого устройства.

### Сценарий 9: Автономность Центра

1. Остановить Центр Безопасности.
2. User A входит / регистрируется.
3. **Ожидание:** Chat API и desktop работают.
4. Запустить Центр снова (`.\scripts\dev.ps1 -Restart`).
5. Новые события появляются в админке.

### Сценарий 10: Общие контакты (когда ingest подключён)

1. User A (Device 1) и User B (Device 2) оба добавляют User D в контакты.
2. **Ожидание:** ребро A—B, тип `shared_contact`.

### Сценарий 11: Переписка (когда ingest подключён)

1. User A и User B переписываются с User D.
2. **Ожидание:** рёбра `communicates_with` в графе.

## Сквозной сценарий

### Сценарий 12: Приватность + наблюдаемость

1. User A и User B на разных устройствах — E2E-переписка.
2. User C создаёт второй аккаунт на устройстве User A.
3. В админке: C связан с A (`same_device`).
4. **Вывод:** платформа обеспечивает приватную переписку и параллельно накапливает данные для анализа мультиаккаунтинга.

## Ключевые тезисы для демо

| Вопрос | Ответ |
|--------|-------|
| Где ключи? | Только на клиенте |
| Видит ли сервер сообщения? | Только ciphertext |
| Как выявляется мультиаккаунтинг? | Граф связей: устройство, контакты, переписка |
| Почему не баним сразу? | Сначала наблюдение и расследование, потом политики — см. [roadmap.md](./roadmap.md) |
| Почему Центр отдельно? | Автономность, изоляция данных безопасности |
